# Транспорт, кодировка, подключение

Обозначения — в [overview.md](overview.md#как-читать-документы).

## Транспорт и кадрирование

### Flash socket policy

Перед открытием игрового сокета Flash Player запрашивает политику безопасности. Ниже приведён пример запроса по отдельному TCP-соединению к тому же серверу.

```
C→S: <policy-file-request/>\0
S→C: <cross-domain-policy>\n<site-control permitted-cross-domain-policies="master-only"/>\n<allow-access-from domain="*" to-ports="*"/>\n</cross-domain-policy>\n
S→C: \0
```

После ответа соединение закрывается, и плеер открывает игровое соединение.

### Клиент → сервер

Каждое сообщение — отдельный кадр (`NSocket.sendStr`):

```
+----------------+---------------------------------+
| uint32 LE      | N байт текста в CP1251          |
| N = длина      | "код|поле1|поле2|..."           |
+----------------+---------------------------------+
```

- Длина записывается как `str.length` — число символов строки ActionScript (UTF-16), а не число байт.
  Это совпадает с количеством байт только для символов, которые кодировщик переводит в один байт (см. [кодировку CP1251](#кодировка-cp1251)).
- Терминатора нет, `#` в конце не ставится.
- Поля склеиваются через `|` методом `GameSocket.send(code, ...args)` или вручную через `sendStr`.
- У части команд в конце стоит лишний `|` (`lg|login|pass|`, `az|`, `za|`, `ec|id|pass|`, `pb|...|`, `sa|...|`). Сервер, по-видимому, его допускает.

Пример кадра в шестнадцатеричной записи.

```
13 00 00 00  6c 67 7c 4c 61 7a 6c 6f 7c 71 61 7a 77 73 78 31 32 33 7c
len=19       l  g  |  L  a  z  l  o  |  q  a  z  w  s  x  1  2  3  |
```

### Сервер → клиент

Поток текста в CP1251, сообщения завершаются символом `#` (`NSocket.socketDataHandler`):

```
код|поле1|поле2|...#код|...#
```

Алгоритм приёма:

1. Новые байты декодируются из CP1251 и дописываются в буфер `sockData`.
2. Буфер режется по `#`. Все части, кроме последней, — готовые сообщения. Последняя (возможно, неполная) остаётся в буфере.
3. Каждое сообщение режется по `|` в массив строк `getData`, `getData[0]` — код команды.

Особенности:

- Экранирования нет. Символы `#` и `|` не могут встречаться внутри полей, сервер должен их вырезать.
- Сервер часто ставит `|` перед `#`, поэтому последний элемент массива — пустая строка. Циклы разбора списков в клиенте идут до `length - 1` и рассчитаны на это.
- Пустое поле (`||`) — пустая строка; при `int()` она даёт 0.
- Числа — десятичный текст. Дробные — с точкой (`1000.00000`).
- Булевы значения — `0`/`1`.
- Счётчики пар/записей в списках всегда предшествуют самим записям.

## Кодировка CP1251

### Приём

`readMultiByte(n, "x-cp1251")` — стандартное декодирование Flash Player. Проблем нет: CP1251 однобайтовая.

### Отправка

Своя реализация `NSocket.writeCP1251String()`: строка переводится в UTF-8, затем UTF-8-последовательности вручную пересчитываются в байты CP1251:

| UTF-8 | Символы | Результат |
|---|---|---|
| `00–7F` | ASCII | байт как есть |
| `C2 xx` | U+0080–U+00BF (`«`, `»`, `©`, `°` и т.п.) | байт `xx` (совпадает с CP1251 для большинства знаков) |
| `D0 xx` | U+0400–U+043F (`Ё`, `Ђ`…`Џ`, `А`–`Я`, `а`–`п`) | таблица `CHARS_D0[xx − 0x81]` |
| `D1 xx` | U+0440–U+045F (`р`–`я`, `ё`, `ђ`…`џ`) | таблица `CHARS_D1[xx − 0x80]` |
| `E2 80 xx` | `–`, `—`, `‘`, `’`, `‚`, `“`, `”`, `„`, `†`, `‡`, `•`, `…`, `‰`, `‹`, `›` | отдельные коды (см. код) |
| `E2 82 xx` | `€` | `0x58` (`X`) — см. [дефекты](client-defects.md) |
| `E2 84 96` / `E2 84 A2` | `№` / `™` | `0xB9` / `0x99` |
| прочее | | байты UTF-8 уходят как есть |

Сервер ожидает именно CP1251. Если писать свой клиент, проще использовать штатный кодек CP1251 и считать длину в байтах после кодирования.

## Подключение, повторы, HTTP-прокси

### TCP

`NSocket.connectGame()` сбрасывает счётчик попыток и вызывает `connect(host, 5190)`.

- При `IOError` или `SecurityError` следующая попытка через `1000 + (n − 1) × 500` мс, где n — номер попытки (1000, 1500, 2000 мс).
- После 3 неудачных попыток, если не выставлен `stopConnecting`, клиент переключается на HTTP-прокси (`connectViaProxy`) и показывает `IDS_CANT_CONNECT`.
- При закрытии сокета сервером выставляется `stopConnecting = true`. Если игра уже шла, показывается `IDS_CONNECTION_CLOSED`. Автоматического переподключения нет.

После успешного подключения (`Main.socketConnectHandler`):

1. запускается пинг: `pg` сразу и затем каждые 20 с (`Main.ping` → `GameSocket.sendPing`);
2. отправляется логин (`FightSocket.loginFight`).

Сервер на `pg` ничего не отвечает.

### HTTP-прокси (резервный канал)

Если клиенту недоступен TCP-порт, он использует HTTP-прокси.

1. **Открытие сессии.** `POST http://<host>/webrule.fcgi` с пустым телом. Ответ — текст `sockId:hash`.
2. **Отправка.** Каждое сообщение — отдельный `POST /webrule.fcgi`, `Content-Type: application/x-www-form-urlencoded`. Тело:
   `sock=<sockId>&hash=<hash>&put=` + байты сообщения в CP1251.
   Префикса длины нет, URL-кодирования данных тоже нет.
3. **Приём.** Один `NURLLoader` в цикле шлёт `POST /webrule.fcgi` с переменными `sock=<sockId>&hash=<hash>`. Ответ — тот же поток `...#...#`, что и по TCP. Следующий запрос уходит через 50 мс после ответа; при ошибке запрос повторяется сразу.
   Ответы на POST-запросы отправки тоже разбираются как входящие данные.
4. После получения `sockId:hash` клиент считает себя подключённым и шлёт логин так же, как в TCP-режиме.
