# Транспорт, кодировка, подключение

Обозначения — в [overview.md](overview.md#как-читать-документы).

## Транспорт и кадрирование

### Flash socket policy

Перед открытием игрового сокета Flash Player запрашивает политику безопасности. Ниже приведён пример запроса по отдельному TCP-соединению к тому же серверу.

```
C→S: <policy-file-request/>\0
S→C: <cross-domain-policy>\n<site-control permitted-cross-domain-policies="master-only"/>\n<allow-access-from domain="*" to-ports="*"/>\n</cross-domain-policy>\n
S→C: \0
```

После ответа соединение закрывается, и плеер открывает игровое соединение.

### Клиент → сервер

Клиент отправляет каждое сообщение отдельным кадром.

```
+----------------+---------------------------------+
| uint32 LE      | N байт текста в CP1251          |
| N = длина      | "код|поле1|поле2|..."           |
+----------------+---------------------------------+
```

- Клиент записывает в префикс длину текста в кодовых единицах UTF-16. При однобайтовом кодировании она совпадает с длиной в байтах. Исключения перечислены в [описании дефектов клиента](client-defects.md#кодировка-команд).
- Кадр заканчивается сразу после текста сообщения.
- Поля разделяются символом `|`. В некоторых командах клиент добавляет `|` после последнего поля, например в `lg|login|pass|`, `az|`, `za|`, `ec|id|pass|`, `pb|...|` и `sa|...|`.

Пример кадра в шестнадцатеричной записи.

```
13 00 00 00  6c 67 7c 4c 61 7a 6c 6f 7c 71 61 7a 77 73 78 31 32 33 7c
len=19       l  g  |  L  a  z  l  o  |  q  a  z  w  s  x  1  2  3  |
```

### Сервер → клиент

Сервер отправляет текст в CP1251 и завершает каждое сообщение символом `#`.

```
код|поле1|поле2|...#код|...#
```

Клиент сохраняет неполное сообщение до получения `#`. Каждый фрагмент до `#` — отдельное сообщение. Первое поле содержит код команды, остальные отделяются `|`.

- `#` и `|` зарезервированы для разделителей и не экранируются.
- Сервер часто добавляет `|` перед `#`. Для списков, идущих до конца сообщения, этот последний разделитель отделяет данные от завершающего пустого поля.
- Пустое поле (`||`) даёт `0`, если клиент читает его как целое число.
- Числа — десятичный текст. Дробные — с точкой (`1000.00000`).
- Булевы значения — `0`/`1`.
- Счётчики пар/записей в списках всегда предшествуют самим записям.

## Кодировка CP1251

Клиент декодирует входящий текст как Windows-1251. Сервер также ожидает Windows-1251 в исходящих от клиента кадрах. Для отдельных символов байты клиента отличаются от стандартной кодировки. См. [кодировку команд](client-defects.md#кодировка-команд).

## Подключение, повторы, HTTP-прокси

### TCP

Клиент подключается к TCP-порту `5190`. При ошибках ввода-вывода или политики Flash Player задержки повторных попыток составляют 1000, 1500 и 2000 мс. После трёх неудачных попыток клиент показывает сообщение об ошибке и переходит на HTTP-прокси. Если сервер закрыл сокет во время игры, клиент сообщает о разрыве соединения. Автоматического переподключения в этом случае нет.

После подключения клиент отправляет `pg`, затем запрос входа. Дальнейшие `pg` отправляются каждые 20 с. Сервер их получает без отправки ответа.

### HTTP-прокси (резервный канал)

Если клиенту недоступен TCP-порт, он использует HTTP-прокси.

1. **Открытие сессии.** `POST http://<host>/webrule.fcgi` с пустым телом. Ответ — текст `sockId:hash`.
2. **Отправка.** Каждое сообщение — отдельный `POST /webrule.fcgi`, `Content-Type: application/x-www-form-urlencoded`. Тело:
   `sock=<sockId>&hash=<hash>&put=` + байты сообщения в CP1251.
   Префикса длины нет, URL-кодирования данных тоже нет.
3. **Приём.** Клиент последовательно отправляет `POST /webrule.fcgi` с телом `sock=<sockId>&hash=<hash>`. Ответ содержит сообщения с терминатором `#`, как по TCP. Следующий запрос уходит через 50 мс после ответа, а при ошибке — сразу.
   Ответы на POST-запросы отправки тоже разбираются как входящие данные.
4. После получения `sockId:hash` клиент считает себя подключённым и шлёт логин так же, как в TCP-режиме.
