### Бросок гранаты

При успешном броске РГ‑42 сервер подтверждает выбор слота через `se|0`. После `ud` сервер отправляет `uw|2000`, обновление веса `0v`, `ef|1` и `fb`. Команда `uw` запускает таймер оружия в интерфейсе. При отказе сервер может ответить `ef|0` без подтверждения слота или сообщения о полёте. Ниже приведён сокращённый пример успешного броска.

```text
C→S ue|0
S→C se|0
C→S ud|15945|-7025|2|-1|-1|-1|-1
S→C uw|2000
S→C ef|1
S→C fb|0|357|56|944|60|938|56|942|0|0|589|2|1
```

В `fb` тип `0` выбирает спрайт гранаты и взрыв, тип `1` — фейерверк. Клиент рисует дугу по параметрам сервера и по завершении полёта сам запускает анимацию и звук в клетке `hitI, hitJ`. Урон сервер сообщает через `ht` для каждой поражённой цели, а смерть — через `dd`. В `fb` нет ID бросившего, а в `ht` нет ссылки на конкретный бросок.

| Бросок | Старт | Прицел | Взрыв | `flyTime`, мс | Результат |
|---|---|---|---|---:|---|
| 1 | (56, 944) | (60, 938) | (56, 942) | 357 | Четыре существа получили урон, одно погибло. Бросивший (`629`) получил 57 критического урона в той же пачке событий |
| 2 | (56, 964) | (64, 954) | (64, 954) | 1432 | `-779` и `-778` получили 27 и 26 критического урона и погибли |
| 3 | (64, 970) | (66, 950) | (66, 950) | 1889 | `-796` получил 31 урон |
| 4 | (60, 968) | (66, 948) | (64, 950) | 1674 | `-796` получил 42 урона |

Во всех четырёх полётах `angle = 2`, `fall = 1`, `mapLevel = blowLevel = 0`. Для второго броска первый `ht` пришёл через 1432 мс после `fb`. Для остальных разница между заявленным временем полёта и приходом урона составила от −68 до +106 мс. Причину расхождения клеток прицела и взрыва и точный радиус поражения по этим пакетам определить нельзя.

### Ход атаки

C→S `at|sessionId` задаёт цель и начинает атаку. До первого выстрела сервер может прислать `mv` для сближения. S→C `at` сообщает о выполненной атаке и содержит клетку цели. Чтобы связать выстрел со своим персонажем, нужно сопоставить эту клетку со своей позицией на момент атаки. Точный момент, когда другое существо выбрало цель, из S→C `at` неизвестен.

В примере клиент получил `sessionId = 84` из `lg`, включил бег через `rn` и двигался по командам `mv`. После запроса атаки `at|-1009` сервер прислал три `mv` для сближения с целью. Через 1,67 с после запроса пришёл `at|84|898|1316|900|1316|7|0|0`, а ещё через 0,52 с — `ht|-1009|5|0` и три ответных `at` существ в клетку `(898, 1316)`.

`ht|84|16|0`, `ht|84|23|0` и `ht|84|25|1` сообщают об уроне по персонажу, а `0e|84|` — о промахе. `ht` и `0e` содержат ID существа, к которому относится результат. При нескольких выстрелах в одну клетку по этим сообщениям нельзя определить атакующего. После последнего попадания сервер отправил `dd|84|0` и `dt|600`.

## Торговля, ремонт, лечение

Сервер увеличивает номер операции `opId` при каждом изменении сделки. В `ac` клиент отправляет последний полученный номер.

| Команда | Формат | Действие клиента |
|---|---|---|
| `ar` | `ar\|userId\|name\|action` | вам предлагают действие → окно с таймером 10 с (`aa`/`al`) |
| `aw` | `aw\|userId\|name\|action` | ожидание ответа собеседника |
| `al` | `al` | закрыть текущее окно действия. Для мирового бартера приходит после завершения безопасного таймера вместе с финальными обновлениями состояния; поэтому сам по себе `al` не доказывает ни успех, ни отмену сделки |
| `am` | `am\|action\|…` | открыть окно сделки: 1 — бартер, 3 — просьба о ремонте, 4 — ремонт, 5 — просьба о лечении, 6 — лечение. Для ремонта и лечения данные начинаются с индекса 8 |
| `bb` | `bb\|action\|-\|tradeSkill\|npcTradeSkill\|npcSessionId\|title\|N\|{item}×N\|{item}…\|` | при `action = 1` клиент открывает торговлю у NPC. Первые `N` предметов — вещи игрока в правой колонке, остальные — товары NPC под заголовком `title` в левой. Цена покупки равна `price`, умноженной на коэффициент от 1,1 до 2,2, который зависит от `tradeSkill − npcTradeSkill`. При `action = 3` или `5` клиент открывает окно ремонта или лечения и читает его данные с поля 7 |
| `bx` | `bx\|-\|-\|-\|-\|sessionId\|title\|N\|{item}×N\|{item}…\|` | контейнер или труп (если `title` не пуст; тогда `sessionId` — труп). Первые N — вещи игрока, остальные — содержимое |
| `cb` | `cb\|shopType\|-\|-\|userPrice\|-\|cellType\|N\|{item}×N\|{item}…\|` | открыть ячейку склада или фабрики. Ненулевой `shopType` включает режим магазина. `cellType` определяет заголовок окна. Значения `5` и `6` относятся к фабрике, `8` — к клановому складу продукции. Списки предметов передаются как в `bb` |
| `ai` | `ai\|opId\|count\|<item>` | собеседник положил предмет ([запись предмета](data-structures.md#запись-предмета)) |
| `af` | `af\|opId\|…` | предмет на ремонт/лечение добавлен |
| `df` | `df\|opId` | предмет убран |
| `th` | `th\|opId\|traum` | травма для лечения выбрана |
| `td` | `td\|opId` | выбор травмы снят |
| `bc` | `bc\|opId\|count\|inventoryId` | количество предмета у собеседника изменилось |
| `di` | `di\|opId\|count\|inventoryId` | собеседник убрал предмет (целиком или часть расходника) |
| `sp` | `sp\|price` | цена изменилась |
| `ac` | `ac` | собеседник подтвердил |
| `bf` | `bf` | подтверждение сброшено |
| `sa` | `sa\|seconds` | таймер безопасной сделки; в мировом бартере после него сервер завершает обработку, отправляет финальные обновления и закрывает окно через `al` |
| `od` | `od\|opId` | новый номер операции |
| `to` | `to\|opId\|traum` | травма вылечена |
| `hf` | `hf` | лечение не удалось |
| `rp` | `rp\|inventoryId\|value` | предмет в инвентаре отремонтирован |
| `ic` | `ic` | закрыть инвентарь и подтверждения |
| `iv` | `iv\|-\|{item}…\|` | открыть инвентарь. Клиент пропускает поле 1, например `10000` |
| `rk` | `rk\|workbenchId\|N\|{recipe}×N` | рецепты крафта. Клиент игнорирует повторный ответ для того же `workbenchId` |
| `rv` | `rv\|workbenchId\|N\|{recipe}×N` | рецепты улучшений, формат приведён ниже |
| `ug` | `ug\|N\|{upgradeCategory\|M\|upgrade×M}×N` | списки улучшений для каждой категории предметов из поля 11 `{item}`. Номера улучшений — от `0` до `25` |
| `ld` | `ld\|…` | журнал ячейки |

Рецепты `rk` и `rv` (`workbenchId` — номер верстака из `02`, типы 24 и 25):

```
rk: id|productCount|group|skillType|skillValue|K|{instrumentId|name}×K|<item>|M|{id|name|count}×M
rv: id|upgrade|skillType|skillValue|K|{instrumentId|name}×K|M|{id|name|count}×M
```

`skillType` = −1 — навык не нужен; иначе нужен навык `skillType` не ниже `skillValue`. Инструменты выводятся одной строкой через `/`.
Ингредиенты с отрицательным id — не предметы. Так, `-3` — рубли: в окне улучшения их количество умножается на `1 + уровень предмета`. Номера от −269 до −292 — наборы улучшений (`WT …` для оружия, `AT …` для брони).
Клиент хранит рецепты `rv` по номеру улучшения `upgrade`, а в запросе улучшения отправляет `id` рецепта. Окно, шанс, цены и пример установки описаны в разделе об [улучшении предметов](upgrade.md).

| `pd` | см. ниже | окно платных услуг |
| `pp` | `pp\|serverDate\|{title\|date\|N\|{id\|name\|image\|type\|currency\|cost×4}×N}…\|` | подарки. Группы идут до пустого `title`. Если `0 < date < serverDate`, подарки группы с `currency = 0` скрываются, а цена подарков-предметов увеличивается в 1,5 раза |
| `pi` | `pi\|N\|{packId\|category\|image\|name\|cost\|discount\|M\|{item}×M}×N\|-\|` | товары магазина. `category` задаёт категорию для фильтра, `discount` — скидку в процентах. Сервер добавляет пустое поле в конце |
| `ud` | `ud\|…` | обновить данные окна услуг |
| `um` | `um\|a\|b` | обновить значения в окне услуг |
| `pe` | `pe\|code` | показать ошибку оплаты с указанным кодом |
| `rm` | `rm\|…` | реферальное меню |
| `pw` | `pw\|code[\|resType]` | ошибка производства: 0 — не тот тип ресурса, 1 — пусто |
| `pn` | `pn\|a\|b\|c` | вопрос «запустить производство?» (ответ — `pn\|1/0`) |
| `ep` | `ep\|a\|b\|c` | показать подсказку о проведённом обмене на бирже терминала |
| `en` | `en` | завершить обмен на бирже терминала |

**Журнал квестов `ql`** содержит пять списков. Каждый начинается со счётчика записей.

```
N|{questId|title|text|placeName|i|j|level|K|{a|b}×K}×N|     текущие квесты; пары {a|b} клиент пропускает
N|{questId|title|text|placeName|i|j|level}×N|                квесты по уровню
N|{title|finishId}×N|                                        завершённые, текст выбирается по finishId
N|{requestId|userId|login|killPrice|killsLeft}×N|            частный найм («Охота на %s»)
N|{userId|login}×N|                                          игроки, назначенные вам целью
```

avatarImg|avatarGoldCost|avatarPalette|

hairColorCost|N|{viewId|cost|goldCost|pal0…pal10}×N|
N|{serviceId|time}×N|                             подключённые услуги; номера 0–2 задают тип аккаунта

## Чат

| Команда | Формат | Действие клиента |
|---|---|---|
| `sg` | `sg\|channel\|sender\|text…` | сообщение в чат, см. ниже |
| `po` | `po\|userId\|name` | открыть приватный канал |
| `cl` | `cl\|{короткая запись}…\|` | добавить пользователей в список чата |
| `cu` | `cu\|<короткая запись>` | добавить или обновить одного |
| `cd` | `cd\|{sessionId\|}…` | удалить из списка чата |
| `dc` | `dc` | очистить списки чата |

Первое поле после `sg` определяет канал сообщения.

| channel | Значение |
|---|---|
| < 0 | приват; канал создаётся при необходимости |
| 0, 2, 3 | общий, торговый, клановый: `text` — текст сообщения |
| 1 | события. `text` содержит `msgId\|args…`. Клиент выбирает текст по `msgId` и подставляет аргументы. Для `msgId = 27` аргументы имеют формат `N\|{name\|count}×N` |
| 5 | событие (в канал событий), формат как у 1 |
| 6 | системное сообщение; `sender == "1"` меняет цвет |
| 7 | системное сообщение в активный канал |
| 9 | журнал клана (или общий канал, если клана нет) |
